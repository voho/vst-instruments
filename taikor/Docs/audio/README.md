# Taikor demonstration audio

Twenty-three rendered examples of what Taikor produces: the twelve strokes of
its vocabulary, the same strokes across all six playable octaves, phrases on
three different drums of the taiko family, every physical control swept across
its range, the close microphone pair opened and backed off, and two longer
musical takes.

Every file here is rendered by [`Tools/RenderDemos.cpp`](../../Tools/RenderDemos.cpp)
from the shipping JUCE-free signal path — the same `TaikoEngine` the VST3, Audio
Unit and Standalone run — so a demonstration cannot drift away from what the
plug-in actually sounds like. No samples, impulse responses, reverbs or external
processing are involved anywhere in this directory: the whole set comes out of
the physical model, including the stereo image, which is two microphones reading
two different points of the same membrane rather than a widener.

## How to listen to them

The set is ordered so it can be played straight through:

- **01–04** are the instrument itself: the stroke vocabulary, then the same
  stroke on every octave. Files 02–04 are the clearest demonstration of the
  octave mapping — twelve strokes per octave, and the octave chooses the drum.
- **05–07** are the same phrase played on the largest, the reference and a small
  tight drum, which is the same comparison heard musically rather than as a
  ladder.
- **08–17** sweep one control at a time. Nothing else changes inside a file, so
  each one isolates a single axis of the model.
- **18–19** are the close pair: distance first, then spread. Listen to these in
  headphones — 19 in particular starts mono and opens up, and it does so because
  the two microphones begin at the same point on the head and walk apart.
- **20–23** are performance: the hand damping the head from CC1, the pitch wheel
  pressing it sharp, rolls and flams, and a longer ensemble piece moving between
  three drums.

## Levels

Each take is rendered with generous headroom and then normalised to −3 dBFS, so
the files can be auditioned one after another without reaching for the volume.
The renderer refuses to write a take that reached full scale before
normalisation, because such a file would have been through the engine's output
limiter and would be documenting the limiter rather than the model.

The **rendered peak** column below is the level the model produced before that
normalisation, relative to the plug-in's own output stage at the reduced gain
the renderer uses. It is the honest measure of how loud each take actually is:
the odaiko phrase and the ensemble piece are genuinely far louder than the ghost
strokes in the velocity take.

## Regenerating them

```bash
cd taikor
cmake -S . -B build-dsp -DCMAKE_BUILD_TYPE=Release \
  -DTAIKOR_BUILD_PLUGIN=OFF -DBUILD_TESTING=OFF
cmake --build build-dsp --parallel --target TaikorRenderDemos
./build-dsp/TaikorRenderDemos Docs/audio
```

The render is deterministic, so running it on an unchanged model rewrites the
same bytes and commits nothing. The repository's Nightly workflow does exactly
this and commits the result only when the audio has genuinely changed, which
keeps this directory in lockstep with the code. The table above is regenerated
in place by the same command, so the documented levels cannot drift away from
the committed files either.

A take that is renamed or removed from the renderer's table is deleted from this
directory on the next full render, so a stale WAV cannot survive here after the
demo that produced it has gone.
